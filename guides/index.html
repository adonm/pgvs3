Workload guides

Keep OLTP in PostgreSQL SQL. Use pgvs3 for object bytes, shared object caching, durable origin staging and bounded companion queues. It does not make arbitrary application SQL faster, implement CDC or turn PostgreSQL into a distributed columnar engine. Start with the path that removes your bottleneck, not with every interface enabled.

Decision tree: choose the model and path

What is the primary access and mutation contract?
├── Point reads/writes, strict ACID constraints, <10 ms OLTP p99
│   └── Keep in PostgreSQL SQL (docs/guides/postgres.md)
│       ├── Wide columns (>2 KiB TOAST / blobs)?
│       │   └── Split hot narrow row from cold payload table, or store multi-MiB blobs in pgvs3
│       ├── Need 32–64 zero-maintenance partitions across 10M–1B+ rows?
│       │   └── Fixed HASH(id/tenant_id), or 32–64 quantile RANGE bounds on 1D Hilbert/Morton curve_id (avoids hotspot skew)
│       └── Only use time RANGE partitions if you must DROP/DETACH whole expired months
├── Analytical scans, aggregations, or billion-row history (minutes-to-hours freshness)
│   └── Extract to Parquet / DuckLake on pgvs3 (docs/guides/analytics.md)
│       ├── Single-table/snapshot export? ──► Immutable Parquet + conditional manifest
│       ├── Entity / tenant / ID filters? ──► Fixed PARTITIONED BY (bucket(32..64, id)) + SORTED BY (ts, id)
│       ├── 2D/spatiotemporal filters (including skewed hotspots)?
│       │   └── High-res 32/64-bit Hilbert/Morton SORTED BY (curve_id, ts) (row groups & target_file_size auto-split dense hotspots by row/byte quantiles!)
│       ├── Billion rows + wide columns? ──► Byte-bounded row groups, skip_stats_columns, late materialization
│       └── Willing to pay slow/batch writes for peak read speed?
│           └── Batch sorted ZSTD writes + merge/rewrite compaction (or sealed ObjFS/DuckDB for heavy joins)
├── Shared S3/HTTP acceleration or durable write-back staging across workers
│   └── Origin-backed pgvs3 cache/stage (docs/guides/cache.md)
└── Asynchronous background work or fan-out from committed SQL changes
    └── Application SQL outbox + OJS jobs/streams (docs/guides/jobs.md)
I need to… Start here Success means
Protect transaction latency while adding analytics/cache/jobs Protect OLTP Measured application tails, connection waits, WAL and vacuum remain inside your budget.
Model schemas, wide columns, spatiotemporal partitions or batch-for-read DuckLake Publish analytical snapshots Tight file/row-group pruning, bounded writer RAM and catalog stats, and explicit freshness/compaction cost.
Reuse S3/HTTP bytes across clients and gateways Cache and staging Another gateway serves the same bytes without an origin fetch; TTL and pending-write authority are understood.
Reliably hand committed application work to HTTP workers Jobs, outboxes and streams Rollbacks enqueue nothing; retries and worker crashes do not duplicate the demonstrated SQL effect.
Diagnose latency, capacity or recovery trouble Observe and recover Identify the constrained resource, preserve acknowledged data and verify recovery before routing traffic.

For setup use the quick start. For flags/API and topology details use operations, not a copied deployment preset. Sources records the research behind these decisions; validation separates executable evidence from deployment advice.

Memory, disk, network and CPU trade-offs

Every optimization moves cost between four hardware budgets. Name which resource you are spending and which one you are saving before changing a schema or knob:

Design choice Memory (RAM) Disk & PostgreSQL WAL Network / HTTP I/O CPU
Restrictive types (BIGINT/INT/TIMESTAMPTZ vs VARCHAR/UUIDv4) Shrinks DuckDB execution vectors and hash/sort state; avoids non-evictable ART index buffers when omitting PKs. Smaller Parquet pages, smaller PG indexes, tighter zone maps. Fewer bytes transferred per column chunk. Faster vectorized comparisons, hashing and bit-unpacking.
Wide-column projection + late materialization + skip_stats_columns Avoids buffering wide strings/blobs during filtering, grouping and sorting. Keeps ducklake_file_column_stats small in the PG catalog; avoids TOAST churn. Transfers only narrow filter/key column chunks; wide chunks fetched only for matched rows. Skips ZSTD decompression and string decoding on unreferenced columns.
Byte-bounded row groups (parquet_row_group_size_bytes) on wide tables Prevents 122,880 × wide_row from buffering hundreds of MiB per writer thread. Slightly more row-group metadata headers; finer pruning granularity. Smaller byte-range fetches for selective queries. More row-group footer checks; lower spill risk.
Fixed 32–64 partitions (bucket(32..64, id) or 64-cell Hilbert prefix) + SORTED BY Sorting/compaction buffers a batch in writer RAM (or spills to temp_directory); bounded catalog metadata. Zero DDL cron maintenance; fixed bucket count prevents small-file explosions across years while target_file_size splits growing buckets cleanly. Prunes to 1..k of 32–64 buckets, then skips non-overlapping row-group byte ranges on the sort key. Pays sort CPU once on batch write/merge to save scan CPU on every read.
Batch write-for-read (SORTED BY, high zstd, merge/rewrite) Higher batch writer/compactor RAM; lower reader buffer footprint. Rewrites small/deleted files (extra PG WAL + reaper work during batch window); smaller steady-state footprint. Minimum GET requests and byte transfer; zero delete-file merge-on-read fetches. Heavy batch sort + ZSTD compression CPU; minimal query decompression/filter CPU.
pgvs3 shared origin cache (s3c_) & range caching Uses PG shared_buffers + OS page cache (and gateway spool ≤8 MiB in RAM). Cold fills write logged PG chunks rows and WAL; consumes vacuum/reap capacity. Eliminates repeated upstream S3 GETs across gateways and standbys. Zstd block check on fill; low CPU on warm PG bitmap heap scans.

Six different kinds of state

Layer Who computes/owns it? Freshness and durability boundary
Application SQL rows PostgreSQL/application SQL transaction; indexes/plans matter. pgvs3 does not intercept these queries.
Native objects pgvs3 + PostgreSQL One object’s committed publication; logged bytes. No transaction spanning an application’s SQL and an HTTP PUT.
Shared origin-byte cache pgvs3 s3c_ rows TTL/version revalidation, not SQL-result invalidation. Fills write PostgreSQL WAL.
Pending origin writes pgvs3 s3w_ + outbox Acknowledged bytes may exist only in PostgreSQL until origin handoff. Not disposable or TTL-expiring.
Analytical materialization DuckDB/DuckLake/application Extract/catalog snapshot and its refresh schedule. pgvs3 transports bytes, not source-table changes.
Jobs / stream deliveries OJS / application workers Leases or acknowledged batches; effects and HTTP acknowledgements are separate commits. Expect redelivery.

DuckDB buffers, Parquet metadata caches and native-extension caches are client-private, not pgvs3 shared-cache hits. A SQL results cache is yet another layer: pgvs3 has no automatic one. If storing application results via RESP, the application must define keys, invalidation, TTL, stale serving and sensitive-data scope; co-location does not supply them.

Decide what you are optimizing

Write down before changing settings:

  1. Correct answer: source of record, allowed staleness, delete/update handling, idempotency key, RPO/RTO and which replica may serve the read.
  2. Budget: application p95/p99 and error rate, object ACK latency and drain rate, refresh lag, queue age, disk/WAL/scratch headroom and connection ceiling.
  3. Experiment: control and candidate, identical 10 MiB–1 GiB files/queries, cold/warm definitions, concurrent OLTP and retained failures. Change one axis.
  4. Acceptance: report each affected path independently. The project’s 20% regression budget is not permission to breach a stricter application SLO. Roll back the setting or move the workload off-cluster if that SLO fails.

More gateways increase client handling capacity, not PostgreSQL CPU, WAL, disk or autovacuum isolation. Separate schemas, databases, roles and pools are ownership/admission boundaries, not resource reservations. Use another cluster or external analytical storage when a shared cluster cannot meet both budgets.

Try it without touching a real database

just setup
just guides

Requires Docker, the mise toolchain and access to the official DuckDB extension repository. This reuses the existing disposable two-gateway/origin harness, runs named snippets from these pages and retains guides.json, query plans and failure evidence under the printed .tmp/verify/guides.*/ directory. It creates only fixture-owned data; it is not a load test or cloud qualification.

For a manual walkthrough, start the quick-start gateway, use a disposable database, and have pgvs3, psql and curl on PATH plus a DuckDB 2.0 session. In the client terminal set:

export PGVS3_URL='postgres://postgres:postgres@127.0.0.1:5432/pgvs3_bench?sslmode=disable'
export PGVS3_ENDPOINT='http://127.0.0.1:8014'

Then follow PostgreSQL → analytics → jobs. These examples reserve guide_app, guide-analytics, guide-jobs and guide-events; stop if those names already contain your data. Recipe SQL mutations are to application-owned demo tables, not pgvs3 internals. The test alone advances one owned terminal job’s age to exercise normal retention without a day-long wait. Cache experiments use a separately owned test origin.

No public endpoint or tenant boundary. The listener never authenticates, authorizes or terminates TLS. Anyone who can reach it can read or destroy all namespaces. Keep it private; dummy S3 credentials are not access control.

What to read after a successful trial

  • Native versus origin-backed costs and replica proof.
  • Per-path benchmark acceptance and capacity capture.
  • DuckLake, Differential and ObjFS trade-offs.
  • Authority, acknowledgements and multi-worker invariants.

The quality bar here is inspectable: prerequisites, state ownership, runnable recipes, expected results, negative cases, measurement, recovery and safe cleanup. The named reference projects inform that bar; no unmeasured vendor-performance or universal-replacement claim is implied.
