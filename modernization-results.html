Modernization implementation and performance comparison

This is completed implementation/evidence history across v24/v25, not the active backlog. See design.md for the current contracts and roadmap.md for ranked next work.

Date: 2026-10-28. Control: a879472 (layout v23). Candidate: layout v24.

This implements the highest-value bounded changes from the capability review, retaining PostgreSQL 18+, logged shared state, the one-port trusted-network model, and specialized object streaming. Fresh databases are required; there is no layout migration.

Implemented

  • Shared parent metadata for range-only caching. Logged, schema-local records cache size, origin validator and headers, but never represent a body. Validation uses the database clock and excludes time spent waiting for HEAD. TTL/retention, mutation fences, flush/drop and read-only consumption are covered.
  • One-round-trip cache shadow resolution. Write-back ownership/tombstones take precedence over shared read cache in one PostgreSQL query. Missing or partially initialized cache namespaces retain independent-lookup fallback.
  • Renewable, publication-fenced fill ownership. Owner-token renewal uses the database clock. Publication locks/checks live ownership and the origin version; an expired, cancelled or superseded owner cannot publish. Waiters do not cancel the owner and have explicit, fetch-budget-aware fallback limits.
  • Shared disk spool byte admission. Fills, foreground writes and pending uploads share a configurable 8 GiB payload budget. Unknown-length growth is nonblocking to avoid partial-reservation deadlock. Cleanup is idempotent; known-size copies retain file-copy fast paths. Exhaustion is retryable before acknowledgment; acknowledged pending bodies remain logged in PostgreSQL.
  • Outbox wake hints. Successful durable publication wakes a local worker instead of always waiting for the idle poll. The buffered hint is lossy and carries no job authority; database claims and one-second cross-gateway/crash fallback polling remain unchanged.
  • PostgreSQL 18 publication SQL. Inline and chunked entry points share one mutation. RETURNING old.file_id, old.parts supplies garbage ownership without an unconditional pre-read. TTL, CAS, multipart metadata cleanup, origin fences and body/outbox atomicity remain transactional.
  • Cache retirement safety. External origin changes retire only the observed write-cache generation. Old fill ownership and read-cache fences are removed atomically, preventing stale-fill resurrection without hiding the new origin. Newer publications and authoritative delete tombstones remain protected.
  • Compatibility and diagnostics. Missing keys are distinct from missing buckets, restoring static-index fallback. Namespace stats have the correct result shape. Partial payloads do not advertise whole-object checksums. Warm range hits are reported accurately. Helm scratch resources and spool metrics are aligned, and durability/pooling/quota documentation is qualified.

Preserved: unconditional multipart write-back, including small multipart bodies. The end-to-end test now waits for asynchronous origin persistence rather than incorrectly requiring the origin file to exist before acknowledgment. Session key locks remain around remote writes; a local token check alone cannot stop a stale remote upload.

S3 origin-client experiments

Compared the existing fork with AWS SDK Go v2 S3 v1.114.6 and MinIO Go SDK v7.4.1. Experiments live in the isolated test/s3clients module, not the gateway dependency graph or binary. These are equivalent HEAD/GET/single-PUT transport comparisons, not a claim of full replacement compatibility.

The isolated experiment used a loopback HTTP origin with no storage backend, checksum validation or signature verification. Clients still signed requests; implicit retries, payload hashing and additional checksum work were disabled where appropriate to match the existing client. MinIO used its low-level Core single-PUT API rather than silently switching to multipart at smaller sizes. Five repetitions used 250 ms benchmark windows; table values are medians.

Gateway comparison methodology

  • Same host: AMD Ryzen 7 7700X, Linux/amd64, Go 1.27.3.
  • Same PostgreSQL 18 instance for both disposable databases, 1 GiB shared_buffers, synchronous_commit=on, and worker AIO. No UNLOGGED storage.
  • Separate control/candidate processes and databases; identical client and fixture bytes. Request order alternates before/after across five repetitions.
  • Actual Snappy Parquet fixtures generated with DuckDB 2.0, with 122,880-row groups: 10,490,851; 67,128,878; 268,489,564; and 1,073,940,706 bytes. The largest is approximately 1 GiB, 0.019% above that exact byte boundary.
  • HEAD, GET, footer ranges and PUT at concurrency 1 and 4. S3 signing is omitted in the gateway load generator because signatures are intentionally ignored; both binaries use that same client. Transport experiments above still sign.
  • Relevant per-case gates: candidate median p50 time <= 1.20 × control and median throughput >= 0.80 × control. Percentiles from small fixed large-object batches are diagnostics, not a production p99/SLO claim.

Rejected initial run

The first cumulative-overwrite run is retained in .tmp/modernization/native.json and native.log. It was not accepted:

  • 10 MiB GET measured 6.372 → 10.289 ms at concurrency 1 and 8.365 → 11.321 ms at concurrency 4, over budget.
  • Concurrent 1 GiB candidate PUTs eventually hit the client’s 60-second timeout.
  • PostgreSQL logged frequent checkpoints, heavy checkpoint sync, vacuum and approximately 39 GiB chunk relations in each database. The workload accumulated overwritten files while the default 1 GiB WAL budget introduced checkpoint phase differences; planner statistics also differed between the databases.
  • A subsequent GET check on the unchanged binaries measured 10.963 → 9.762 ms, demonstrating that the original read difference was not stable. The initial query plans were not captured, so this is not a definitive single-cause diagnosis.

The controlled rerun explicitly analyzes read fixtures, uses fresh buckets for each PUT batch, matches checkpoints outside timed work, and uses a 16 GiB WAL budget / 30-minute checkpoint timeout on the benchmark instance only. This does not change production durability or silently tune a user’s database.

Native S3 acceptance

The controlled matrix completed all 400 runs without request errors or timeouts. Thirty-nine of forty short-run cases passed directly. Concurrent 10 MiB GET still showed +26.2% p50 in its seven-request batches, so it was not waived: five paired 1,000-request steady-state runs per binary followed. Median p50 was 11.304 → 11.240 ms (-0.6%), median throughput 326.416 → 328.873 requests/s (+0.8%), with zero errors. Both databases used matching bitmap heap/index scan plans. Final dependency/security check

The full vulnerability check found pre-existing GO-2026-6617 in golang.org/x/net v0.59.0. Production now uses the fixed v0.60.0; no AWS or MinIO dependency was added to the gateway module. A same-database follow-up compared the pre-patch candidate with the final binary: 4 KiB HEAD 0.106 → 0.109 ms, concurrent ~10 MiB GET 10.567 → 10.791 ms, ~1 GiB GET 939.534 → 946.253 ms, and concurrent ~1 GiB footer ranges 0.284 → 0.287 ms. All were within 3%, without errors. The primary matrix above predates only this HTTP/2 dependency security patch and local outbox wake hints (which do not run on native read paths); the representative final-binary check is recorded in .tmp/modernization/security-http-smoke.json.

Reproduction and evidence

test/loadgen now supports fixed S3 request counts, unsigned comparisons, Parquet payload files and range offsets. It checks body-copy errors rather than counting a truncated response as success.

deploy/bench/compare.py drives that existing load generator; it is not a new load engine or conformance framework. It requires disposable endpoints/databases. --postgres-before / --postgres-after enable explicit ANALYZE/checkpoint preparation, and --isolate-writes creates/drops a fresh bucket per PUT run.

The measured run records and client benchmark output are also retained in benchmarks/modernization-2026-10.json, without database credentials. It includes the rejected short-run gate and its explicit steady-state replacement, not just favorable aggregate numbers.

Example, after building control/candidate binaries and the common load generator:

python3 deploy/bench/compare.py \
  --before http://127.0.0.1:19114 --after http://127.0.0.1:19124 \
  --loadgen .tmp/modernization/loadgen \
  --payload .tmp/modernization/parquet-10MiB.parquet \
  --payload .tmp/modernization/parquet-64MiB.parquet \
  --payload .tmp/modernization/parquet-256MiB.parquet \
  --payload .tmp/modernization/parquet-1024MiB.parquet \
  --postgres-before "$BENCH_BEFORE_URL" --postgres-after "$BENCH_AFTER_URL" \
  --isolate-writes --repeats 5 --out .tmp/modernization/native-isolated.json

Use --seed-endpoint with --ops range,head for a range-only origin-cache comparison. Seed directly at the origin, not through the proxy: a proxy PUT or full GET would warm the write-back/whole-body cache and invalidate that experiment.

Validation: unit/race tests, PostgreSQL integration with the race detector, the pinned 36-test s3t allow-list, codec/range fuzzing, Helm lint/render, hk check --all --profile ci including vulnerability checks, and the full Docker end-to-end contract including boto3, RESP, OJS, cache tier, DuckDB and DuckLake. New regression tests cover owner renewal/loss, stale inline/COPY publication, read-only range hits, metadata TTL/flush/logging, scratch cleanup/admission, same-ETag newer-write protection and external-origin refresh fencing.

Real AWS/Aurora performance, actual replica promotion and production tail latency remain unverified. Logged state and local commit durability are not a promise of lossless promotion of an asynchronous replica.

Capability-consolidation follow-up

The organization-only pass (173 → 140 Go files) was followed by a capability refactor against the captured 140-file binary. Both use layout v24. The result is 47 Go files, including tests. The 10-file vendored client is now the five-file internal/s3client package:

internal/s3 30 6

This pass also changes ownership and shared implementations:

  • One native and one origin S3 adapter implement read/write/multipart capabilities, with one backend-selection policy. In particular, origin part copies cannot accidentally take the native fast-copy path.
  • One registry map and replacement loop own both global and per-bucket tiers. Unchanged specs reuse their tier; failed replacements retain the working tier.
  • Foreground and outbox mutations share local/session-lock ordering and failed acquisition cleanup. Body validation still precedes database-lock acquisition.
  • Six ordinary stream operations now use the store’s existing transaction lifecycle. Maintenance transactions that deliberately roll back no-op or missing-schema paths remain explicit.
  • Both pool policies share failed-open cleanup. Writable and read-only startup use the same layout validation.

Readability and code-quality follow-up

The final pass removes ordinary comments from first-party Go code. Only compiler directives (//go:build, //go:embed) and vendored license headers remain. Readability now comes from names, capability-sized interfaces and sectioned implementations.

Specific simplifications:

  • pgx.Batch now sends job rows and global index rows in one round trip instead of two statements per job.
  • RESP EXISTS groups cache keys into one query while preserving duplicate-key semantics and s3:// bucket reads.
  • Origin registry lookups use an atomic refresh clock and reader lock; tier construction and closure happen outside the reader lock.
  • Streamed bodies return their first pooled chunk correctly and share one next-chunk/error path between Read and WriteTo.
  • One HTTP-origin request builder applies configured headers and trace propagation consistently to reads, writes and deletes.
  • Namespace relation-size SQL and chunk-layout checks have one definition each.
  • CRC-64/NVME uses slicing-by-8 tables and is verified against a bitwise reference.
  • Standard library helpers replace local itoa, lower, manual hex/ETag validation, manual ISO-8601 assembly and one-off sorted-map loops.
  • The S3 client now lives in internal/s3client; the misleading nested module and replace chain are gone. Loadgen and the client share one SigV4 signer, and the plain-HTTP origin shares the same pooled transport policy.
  • S3 route handlers return errors; one mapper converts store/origin failures into S3 codes. 145 scattered writeError branches collapsed into that path.
  • Store *Ref suffixes are gone, upload/part/completion variants use one method with options, and withSchema centralises missing-schema reads.
  • S3, OJS and RESP metrics share internal/telemetry; parameter structs replace the longest positional call sites; time-driven tests use testing/synctest.

Handles, splits, read views and loadgen

That round kept layout v24 and the S3, OJS and RESP behaviour. The Now column above counts the tree at 2857200.

  • Namespaces are bound once. Store.Cache(name) and Store.Queue(name) validate the name and resolve its schema when the handle is created, so cache and stream methods stop repeating that work per call. OJS depends on the store.QueueHandle interface, which keeps its HTTP tests on a small fake. Lifecycle methods stay unexported on the concrete queue type.
  • Long functions were split. Top-level production functions longer than 80 lines fell from 17 to 7, and the longest fell from 230 to 109 lines. The split covered serve, OpenWithOptions, ChunkWriter.run, copyObject, Diagnose and StatNamespace.
  • Object reads pass one readView value that carries the span, size, validators and metadata. newObject is the only place that builds &Object{...}. openRange takes four parameters instead of twelve, and the unused resolveCache key argument is gone.
  • The load generator runs every protocol through one measurement harness. test/loadgen/main.go fell from 751 to 612 lines. The 550-line target was not reached: the remaining lines are flag declarations and per-protocol requests.
  • Not done: moving stream SQL into schema functions, which is a layout change that needs an explicit decision, and collapsing the in-memory and filesystem origins. Their keys mean different things (opaque strings versus paths), so a collapse would change behaviour.

Whole-repo lines rose by 148 in this round. Extracted helpers repeat signatures (the split adds 200 net lines), the handle file and its test adapter add code, and the loadgen harness shrank by 139. The gain is in complexity, not line count.

Layout v25, local origins and test trim

This round moves to layout v25 and simplifies two more areas. Layout v25 needs fresh databases; there is no migration from v24.

  • Stream operations are layout-v25 SQL functions. Each queue schema gets stream_* functions for append, subscribe, receive (plain and cooperative), batch read, ack, nack, retry processing, prune, rotate and replay. Each call is one statement, so a request is one round trip instead of five to thirteen. stream.go lost about 800 lines and schema.sql gained about 430. Go keeps validation, namespace creation and sentinel mapping. A missing queue or batch still returns the same not-found result. Partial schemas (an undefined table or function) propagate as storage errors instead of reading as empty, and doctor lists queue namespaces that lack stream functions.
  • Local origins collapse into one implementation. filesystem and ephemeral share one os.Root-based implementation. The temporary-directory origin kept its old type name in this round because origin set accepted it; it now stores in a private temporary directory that is removed on close. Keys the local origin cannot represent are rejected with 400 before any body is acknowledged. Overwrites write a temporary file under .pgvs3-tmp and rename it under the lock, so concurrent readers never see partial bytes.
  • The test surface is trimmed. Integration test functions went from 100 to 70 (excluding TestMain), integration-tagged test lines from 5,317 to 4,646, and e2e checks from 239 to 159. e2e has no fixed sleeps. Four compact tests cover invariants that had none: layout refusal, a single maintenance leader, chunk storage settings, and split pools. Shared TestMain, discard-logger, deadline poll and namespace-cleanup helpers live in internal/testutil. The 4,400-line target was not met; the largest tests need table rewrites.

Paired checks, layout v25

Catalog bucket rule, ephemeral rename, fault/interop trim and streaming-upload fix

This round completes the three deferred items and fixes a gateway bug that the interop suite exposed.
