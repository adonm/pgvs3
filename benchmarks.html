Benchmarks

The primary workload is 10 MiB–1 GiB Parquet, in native PostgreSQL storage and origin-backed shared cache/staging roles. Current v24/v25 implementation evidence, including actual Parquet and incompressible fixtures, is recorded in modernization-results.md, with rejected trials, accepted per-path gates and remaining validation limits.

This page describes the runners and retains historical measurements. Snapshots from different hosts, layouts and cache states are not one current capacity claim. The focused roadmap ranks physical-replica and WAL/capacity evidence ahead of more protocol benchmarks.

For workload selection, freshness, OLTP budgets and executable SQL/API recipes, use the workload guides. just guides validates those recipes in the existing fixture; it is not a third benchmark or performance acceptance.

Two benchmark harnesses are included in the repository:

  • just load runs test/loadgen directly against the HTTP gateway to measure raw S3 + PostgreSQL throughput and latency, or drives paired acceptance through the existing compare.py with isolated before/after fixtures.
  • just bench runs DuckDB 2.0 and DuckLake through httpfs to measure end-to-end client performance. Its opt-in differential part also measures Differential’s native-storage client through the C++ S3 SDK; just differential is the shortcut. See provisioning and comparison contracts. Recorded findings separate client performance from gateway retry avoidance and retain unsupported workloads explicitly. just object-storage uses the same cohort workflow for the signed SlateDB ObjFS client; its method keeps cache/thread tuning, live-writer reads, sealing costs and read-only endpoint limits distinct. ObjFS results retain both the sealing benefit and the lean profile’s per-path budget misses rather than declaring an aggregate win.

Both harnesses start disposable PostgreSQL 18 containers on loopback. The direct matrix uses shared_buffers=1GB and pool 128; paired runs use pool 32 per binary with separate fresh PostgreSQL clusters so WAL/resource observations cannot mix the two sides. Different layouts never share a database. Each optional physical standby also has 1 GiB shared buffers. Numbers below are from a 16-core local host (Intel Core Ultra X7 358H, 62 GiB RAM) alongside an earlier 6-vCPU / 11 GiB VM baseline.

Direct S3 gateway load (just load)

The exploratory matrix uses 5-second tests. 4 KiB tests use 2,000 keys; 8 MiB and 64 MiB tests use 16 and 8 objects; ListObjectsV2 lists 1,000 keys per page from a 2,000-key bucket. Gateways hold no in-process cache; metadata and ≤64 KiB objects are served directly from PostgreSQL shared_buffers.

Paired acceptance

Save a control binary before making changes, then run the current tree against it:

mkdir -p .tmp
mise exec go -- go build -o .tmp/pgvs3-before ./cmd/pgvs3
# Make the change, then:
just load --before-bin .tmp/pgvs3-before --profile native \
  --payload /path/to/10m.parquet --payload /path/to/100m.parquet \
  --ops head,get,range,put --workers 1,4 --repeats 5
just load --before-bin .tmp/pgvs3-before --profile origin --cache-state cold \
  --payload /path/to/10m.parquet --ops get,range --workers 1,4 \
  --range-size 65536 --repeats 5

--after-bin selects a saved candidate instead of building the current tree. --out selects a fresh output path; existing outputs are never overwritten. Otherwise artifacts and paired.json remain in the unique printed .tmp/verify/ directory. --no-small omits the default 4 KiB case. --requests overrides the size/state-aware per-sample budget; all counts and raw samples are recorded.

compare.py is the only paired driver and still uses test/loadgen, not a second load engine. It alternates binary order, hashes frozen binaries and payloads, checks object/range sizes and bytes, checks persisted origin directory/namespace/ TTL/range settings, and rejects unexpected cache paths. Cold filesystem-origin fixtures use distinct keys with no prior cache bodies or metadata, and validate the completed fills. Loadgen’s opt-in -unique-reads shares one read sequence across workers; its default workload is unchanged. Cold here means cold gateway cache, not cleared operating-system page cache.

Each case fails independently above +20% median p50 or below -20% median request rate, or on any request/fixture error. A valid report has complete: true; partial reports retain complete: false. failed_gates names regressions rather than hiding them in an aggregate. Range labels distinguish aligned chunks, whole-object cache ranges and pass-through. The exploratory matrix remains available without --before-bin, reports saturation errors instead of treating them as acceptance, and writes actual NDJSON. PGVS3_BENCH_DURATION shortens that matrix for fixture smoke tests only; use repeated paired runs for acceptance.

Capacity evidence

Use disposable isolated clusters only. Resource mode deletes its fixture keys, advances their committed-cache expiry deadlines, reaps and vacuums after each case. It refuses pending bodies at cleanup and never advances a pending body’s expiry.

Generate reproducible inputs with the existing DuckDB tool, without a gateway:

mise exec uv -- uv run --quiet --no-project --with duckdb==2.0.0 \
  python deploy/bench/duck_bench.py --parts fixtures --out .tmp/capacity/fixtures.json

This produces approximately 10/100/1,024 MiB Snappy Parquet and exact-size binary fixtures under .tmp/capacity/payloads/. Actual sizes, generation SQL, seeds and SHA-256 hashes are recorded. Binary fixtures repeat a seeded 1 MiB block: they are incompressible at pgvs3’s 8,120-byte block size, not unique random streams across the entire file. --fixture-mib selects smaller smoke inputs; existing files are never overwritten.

just load --capacity --after-bin .tmp/pgvs3-candidate --profile origin \
  --payload .tmp/capacity/payloads/parquet-100MiB.parquet --no-small \
  --ops get,range,put,overwrite --workers 1,4 --range-size 65536 \
  --replication async --checkpoint-writes --repeats 5
  • --capacity uses one candidate endpoint/cluster and the existing loadgen to capture resource costs. It sets mode: capacity, performance_gates_evaluated: false and failed_gates: null; completion means the fixtures/observations passed, not a before/after performance claim. Use ordinary uninstrumented paired runs for the regression gate. Separate clusters on one host still contend for the same physical disk.
  • --resources enables snapshots and observations on separate primary clusters. --replication async|sync adds a real physical standby per side and enables resources. sync selects one named synchronous standby; it does not mean remote_apply. Recovery state, system identifiers and replay positions are validated. Standbys use hot_standby_feedback=on; feedback/snapshots can hold back primary vacuum. No production replication policy is changed.
  • overwrite uses loadgen’s opt-in -overwrite: each worker reuses one prefilled key, retaining retired files for the lifecycle measurement. Ordinary PUT keeps its distinct-key behavior. Use --cache-state cold --ops get,range for empty origin-cache fills; otherwise reads are explicitly warmed and verified.
  • --checkpoint-writes prepares publication/cold-fill samples with a primary checkpoint, replay barrier and standby restartpoint outside timed work. The duration is recorded, not hidden as free work. Use a one-request sample budget for 1 GiB resource cohorts and retain several paired repetitions; larger bursts are a separate sustained-churn experiment, not a peak-throughput comparison.
  • --isolate-origin-put is a separate paired PUT-only filesystem fixture. After drain and byte verification it deletes only that sample’s origin keys; before the next sample it truncates the otherwise empty owned cache tables. It refuses pending bodies, incomplete multipart uploads or unrelated keys and cannot be combined with resource mode. This isolates fresh publication ACKs; it is not a retention/reaping or sustained-upload-throughput measurement.
  • Each raw run records pre-run, post-loadgen and post-drain snapshots: logical object-row bytes, heap/index/total relation bytes, pending state, WAL insertion positions, checkpoint statistics, gateway metrics and standby replay. The post-loadgen snapshot is not the exact instant of the last HTTP ACK. Acknowledgement latency remains loadgen’s per-request measurement; after-loadgen drain is reported separately, not hidden inside ACK throughput.
  • Lifecycle snapshots show delete, injected committed-row expiry, reaping and vacuum separately. Ordinary vacuum makes space reusable but need not shrink relation files. The logical count includes expired rows until reaped. Cleanup verifies the reaper actually drained rather than merely losing the maintenance-leader race, records reaping/vacuum time, and uses the explicit --maintenance-timeout deadline (default ten minutes).
  • WAL bytes are isolated-cluster LSN advancement, including headers/padding, checkpoint/full-page-image and background work—not a per-table WAL counter. Observer pg_settings describe its psql session and cluster defaults, not the gateway’s connection-local SET policy.
  • Gateway gauges use a 100 ms poll interval plus probe time, so their observed peaks are lower bounds. Cross-node WAL position gaps include probe skew; they are not simultaneous end-to-end lag measurements. pgvs3_spool_peak_bytes is exact reserved-payload high water since that gateway started, not a resettable per-case peak. Pool counter deltas also include metrics observations. Replay catch-up time includes SQL/polling overhead.
  • Resource collection can perturb short measurements. Keep the same observations on both sides, retain raw records, and use uninstrumented paired runs to resolve performance-gate failures. Do not silently discard a failed resource comparison.

The paired driver defaults to a five-minute S3 request timeout for large fixtures; --request-timeout changes it. Standalone loadgen keeps its one-minute default and exposes -timeout. A client deadline failure remains an error, not a retry or a successful sample; loadgen stdout/stderr are retained in the failure.

resource_schema: 1 and complete: true identify finished observations. Only a paired report with performance_gates_evaluated: true and empty failed_gates also establishes its measured regression gate. Full configuration and binary/ payload hashes remain in the report. See data-plane-results.md for recorded results and deployment-sizing limits.

Key takeaways:

  • Sub-100 µs RESP reads & 460k GET/s pipelined: a 1-worker 4 KiB GET completes in 0.072 ms (72 µs) p50 (12.2k req/s), scales to 97.0k GET/s unpipelined and 460.4k GET/s (1.76 GiB/s) at pipeline 16 via CacheMGet coalescing.
  • 213k/s durable pipelined RESP writes: pipelined SETs coalesce into one CacheMSet statement, reaching 213.6k durable SET/s (834 MiB/s, 0.28 ms p50) at pipeline 16 (48.2k unpipelined) with the previous LZ4 codec. Re-run just load after the Zstd switch for current numbers.
  • OJS queue benchmarks: the SQS rows were removed with the SQS protocol in the OJS v1 rewrite. Run test/loadgen with -op ojs-enqueue / -op ojs-fetch against a live PostgreSQL to measure the new path; no numbers are claimed here yet.
  • Sub-millisecond S3 small reads & 20.9k/s durable S3 writes: S3 4 KiB GET reaches 35.8k req/s (0.17 ms p50 at 1 worker) and durable 4 KiB PUT reaches 20.9k req/s.
  • Cache tier: a warm 4 KiB GET through the cache proxy costs one PostgreSQL read and reaches 12.2k req/s; 64 MiB reads reach 4.0 GiB/s and write-through PUTs 488 MiB/s (origin is a local filesystem).
  • Cache ranges are passed through: a cold 1 MiB range of a 256 MiB origin object returns in 2.2 ms without caching the body; the first full read takes 0.90 s and the warm read 0.18 s.
  • Multi-GiB/s large-object reads: 64 MiB reads stream at 1.30 GiB/s from 1 worker and 4.17 GiB/s (4,275 MiB/s) across 16 workers.
  • Fast byte ranges and listings: 8 KiB range reads from 64 MiB objects reach 16.1k req/s (3.55 ms p50), and 1,000-key ListObjectsV2 calls reach 1,840 req/s (~1.84M keys/s).

CPU profiles (15s each, Go pprof):

  • 4 KiB GET: getObject 53% cumulative; metaRef 33%; pgx query 22%; socket writes 34%. A dedicated inline-object read path was prototyped and benchmarked. It did not improve throughput (62.4k vs 63.1k req/s at 64 workers), so it was reverted. Query/transport latency, not metadata field decoding, dominates this path.
  • 4 KiB PUT: putObject 44%; putInlineRef 33%; pgx query 22%; socket writes 19%; MD5/SHA ~5.1%; GC ~7%. Preallocating the inline body from Content-Length removed the io.ReadAll growth/copy path and improved the 16-worker PUT result from 24.2k to 26.7k req/s. Reusing the inline buffer from a bounded 64 KiB pool then improved a fresh three-sample mean from 26.3k to 27.3k req/s at 16 workers and 32.2k to 33.3k at 64 workers; the 64-worker p99 fell from about 7.9 ms to 7.3 ms.
  • 64 MiB GET: syscalls 70%; streamRows 59%; pgx row decoding 44%; appendRow 14%; socket writes 33%. A direct-decode experiment skipped the decoded-row → response-buffer copy for unclipped full-object reads, but the result was flat to slightly worse (6.59 vs 6.83 GiB/s at 8 workers), so it was reverted. Large reads remain syscall- and transport-bound.
  • 64 MiB PUT: the framer now writes full rows directly from the incoming buffer and retains only the trailing partial row, removing a full-write copy into pending. An 8-worker three-sample mean improved from 19.8 to 21.0 req/s (1.24 to 1.31 GiB/s); p50 fell from ~399 to ~379 ms and p99 from ~467 to ~436 ms. Parallel MD5/SHA changed throughput by at most about 2% and raised CPU; probes that skipped hashing or compression changed it by less than 1%. Neither path is the next target.
  • Warm cache 4 KiB GET: the warm-hit path was doing two metadata lookups (MetaHeader for the cache decision, then GetBody for the body). Reusing the first metadata row for the body read raised 1/16/64-worker throughput from 7.2k/33.9k/49.7k to 9.4k/39.0k/62.9k req/s, matching native inline GET. The canonical cache row above predates this change.
  • Query execution: the default pgx cache_statement path remains fastest. Switching the whole connection to cache_describe, exec, or simple_protocol reduced 4 KiB GET/PUT throughput by roughly 18–30% at 16 workers, so no query-mode change is retained.

The ownership-aware large-PUT row feed was also built and rejected. It was correct, but the segment/reader path measured about 20.0 req/s versus 21.3 req/s for direct framing: removing the copy did not repay the extra per-row bookkeeping. Large PUT is left at direct framing. A GOGC=200/400 experiment initially looked much faster, but the gain disappeared when the load generator was pinned to its own GOGC=100; the gateway GC target is not a retained change.

The next measured slice is the native 4 KiB PUT query/bind path. The current profile is about 22% pgx query/bind, 19% socket writes, and 5% hashing. The first experiment is a narrow unconditional bucket inline-write path with fewer bound parameters and less server-side branching, benchmarked at 16 and 64 workers against the current 33.3k req/s. It will be kept only if it beats that result. Small GET is at its query/transport ceiling, warm cache GET matches native, and large reads are at the syscall ceiling.

RaQuet raster lookups (just bench raquet)

RaQuet stores rasters in Parquet: one row per 256x256 tile keyed by QUADBIN cell, so a point lookup through DuckDB’s raquet extension is a footer read plus one row group, not a scan. The part generates a deterministic 58.9 MB, 1,024-tile float32 raster (test/raquet_fixture.py, 8 tiles per row group), checks lookups against the generator, then times 400 random point lookups through gateway B, plus one region query and a full scan. Set PGVS3_READ_CACHE_BYTES to measure the gateway read cache.

Measured 2026-11-03 on the 16-thread Intel Core Ultra laptop (±15% between runs):

Point lookup, 1 worker 1 GiB 69 q/s 14.4 ms 19.4 ms
Point lookup, 16 workers off 287 q/s 54.3 ms 85.7 ms

Each lookup makes 9 ranged GETs totalling 645 KiB, with per-GET p50 of 0–3 ms, so most of the per-query time is spent in DuckDB rather than the gateway. The region query (9% of the area) reads 34.8 MiB in 160 GETs in about 0.3 s. Most of its bytes come from Morton-order row groups that only partly overlap the polygon, which is a file-layout property, not a gateway one.

RaQuet on a real orthophoto (just bench ortho)

The same queries on real imagery: an N x N block of the LINZ Wellington 2021 0.075 m urban aerial sheets (CC BY 4.0, Toitū Te Whenua LINZ, AAM NZ and Wellington City Council), RGBA uint8. test/raquet_ortho.py downloads the sheets, checks each against its STAC checksum, and converts the mosaic with CARTO’s raquet-io 0.9.0 in a GDAL container (deploy/bench/raquet-io/), keeping its default full overview pyramid, gzip and 200 tiles per row group. The result is cached in ~/.cache/pgvs3/ortho; PGVS3_ORTHO_SHEETS picks the block (default 8) and PGVS3_ORTHO_FILE benchmarks any other RaQuet file. Each part times 400 RGB point lookups at native zoom, 50 lookups per overview zoom, a region over the central 9% and a band_1 scan, all through gateway B and all checked against DuckDB on the local file.

DuckDB on the local file (page cache) takes 28 ms per point lookup, 1.18 s for the region and 1.39 s for the scan with the default layout. The region is bound by tile decoding in DuckDB; point lookups pay about 26 ms to move 22 MB, because each lookup fetches one row group’s column chunk for each of three bands. Row-group size, not the gateway, is the main lever for raster lookups.

On a cold read-through cache with the contract’s 64 KiB --range-cache-chunk, one 22 MB point lookup makes about 315 origin requests, and a cold scan holds S3 admission slots long enough that the default 1 s --s3-queue-wait returns 503 SlowDown to some of DuckDB’s 64 parallel GETs (DuckDB retries them; with PGVS3_S3_QUEUE_WAIT=30s there are none). Raster origins want a larger range chunk. These cold figures predate a fix to the test origin proxy, whose 5-entry listen backlog stalled bursts of new connections for about 1 s; they overstate cold time and should be re-measured.

Iceberg through the cache tier (just iceberg)

Iceberg on S3 is latency-bound: planning reads metadata.json and the manifest list, then each manifest referenced by the current table state, and each is a separate object-store round trip. just iceberg writes a table with pyiceberg 0.12 (SQLite catalog, identity-partitioned by day, one 20,000-row append and one snapshot per day, PGVS3_ICEBERG_COMMITS=100) straight to the origin. DuckDB 2.0’s iceberg extension then reads it in three ways: directly from the origin through a proxy that adds PGVS3_ICEBERG_ORIGIN_MS to every request, through gateway B on a cold cache, and through gateway A warm. The cache bucket maps 1:1 onto the origin bucket (strip_bucket), so the table’s absolute s3:// paths resolve unchanged; clients only switch endpoints. Three more appends then go through gateway A and are read back through B. Every role must match the generated data, and the warm and write-through reads must cause zero origin reads.

Warm reads don’t depend on origin latency: planning-bound queries are 16–50x faster and the full scan 6–15x. Three implementation details shape the warm path. ReadMany serves files whose bytes are in the gateway read cache from memory (metadata still comes from PostgreSQL) and splits the rest across chunk connections. Range responses stream the cached chunk slices instead of copying them into one buffer; a CPU profile had memmove and memclr at 45% of the warm gateway’s time. Range fills now read each missing run from the origin once, publish each aligned chunk to PostgreSQL synchronously with bounded store concurrency, and only then assemble the response. Synchronous publication is a correctness change, not a measured warm gain. A successfully published fill is immediately visible to other gateways sharing PostgreSQL; store errors are best-effort, logged, and the response still uses the fetched bytes.

The first runs of this benchmark found two connection-pool deadlocks that only a burst of concurrent large reads exposes. Cold big one-month took 139 s: range-chunk writers held a main-pool connection while nextFileID waited on the pool for another, so the fills stalled until their 2-minute timeout. Separately, a multi-piece read held its guard connection while its workers waited on the pool, which stalled the native origin for over 2 minutes. File IDs are now allocated on the writer’s own session, and the guard session does the read’s first share of work. A warm big lookup also lost 2 s to ReadMany sorting wide chunk rows into temporary files; it now assembles rows by offset without ORDER BY.

Design ablations

64 KiB inline threshold vs 8 KiB chunking (6-vCPU VM, 1 worker)

Object size & op 64 KiB inline (default) 8 KiB cutoff (chunked)
32 KiB PUT / GET 509/s · 3,619/s 227/s · 1,398/s
64 KiB PUT / GET 356/s · 3,250/s 200/s · 1,272/s

Inlining up to 64 KiB in s3p.objects is 2–3× faster than splitting into s3p.chunks rows.

Single table vs partitioned s3p.chunks

Hash-partitioning s3p.chunks into 16 or 64 partitions slowed 4 KiB GETs by 17–28% and PUTs by 5–21% due to planner overhead without spreading single-file reads. A two-level 8×8 hash/range layout improved single-worker 64 MiB GET from 441 to 556 MiB/s but regressed 4 KiB GETs by 21–32%. s3p.chunks therefore stays a single unpartitioned table; see partitioning.md.

Top 6 takeaways

  1. Latency: pgvs3 serves a 4 KiB GET in 0.17 ms and a durable PUT in 0.78 ms p50, ~10× faster than S3 Express’s single-digit milliseconds.
  2. Small-object reads: pgvs3 peaks at 32.5k GET/s on one 16-core node, ~6× below S3 Express’s 200k/s default bucket quota (2M/s max).
  3. Small-object writes: pgvs3 reaches 17.5k durable 4 KiB PUT/s, ~6× below S3 Express’s 100k/s default quota (200k/s max).
  4. Large-object bandwidth: pgvs3 streams 64 MiB reads at 3.45 GiB/s and writes at 458 MiB/s in cache/NVMe (125–1,000 MiB/s on cold EBS gp3), while S3 Express scales elastically with client network.
  5. 500 GB large-file cost (7,450 × 64 MiB, 1× W+R/mo): S3 Express costs ~$57/mo vs ~$100–200/mo for a dedicated pgvs3 node, or $40/mo in gp3 disk on an existing PostgreSQL.
  6. 500 GB small-object cost (122M × 4 KiB, 1× W+R/mo): S3 Express costs ~$199/mo due to $1.13/M PUT fees, while pgvs3 charges $0 per request and stays at ~$165/mo dedicated or $40/mo on an existing PostgreSQL.
